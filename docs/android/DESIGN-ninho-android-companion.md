# Design: App Android nativo (Device Owner) companion do Ninho

Generated by /office-hours on 2026-10-02

Status: APPROVED
Mode: Startup (produto real)

## Problem Statement
O Ninho (painel web de supervisão familiar) tem banco de dados, autenticação e dashboard do responsável funcionando em produção (Supabase/Lovable Cloud). Falta a peça que torna o produto real: um app Android nativo instalado no aparelho supervisionado, operando como Device Owner, que vincula ao responsável, mantém conexão/telemetria permanentes e executa comandos (localização, foto, screenshot, gravação de tela/áudio, mensagem, alerta) com consentimento visível e auditável.

## Constraints
- Kotlin + Android Studio + SDK atual.
- Device Owner via provisionamento (não pode ser concedido por instalação manual do APK).
- Device Owner só pode ser ativado em aparelho sem nenhuma conta já configurada (estado de fábrica/reset). **Decisão de produto confirmada:** o alvo é um aparelho dedicado (comprado/reservado só para ser supervisionado), não o retrofit do celular que a criança já usa no dia a dia — reset de fábrica como pré-requisito é aceitável nesse cenário e mantém a justificativa de usar Device Owner (bloqueio anti-tamper, kiosk). Se no futuro o produto precisar suportar retrofit de aparelho em uso, isso exige reavaliar a arquitetura inteira (Device Owner pode não ser a escolha certa para esse caso).
- Toda captura sensível (câmera/tela/áudio) exige indicador visível do Android e consentimento auditável — sem captura oculta (requisito do usuário, e já formalizado como regra do projeto em `AGENTS.md` do repo Ninho). Consentimento aqui significa: a criança/aparelho supervisionado vê um aviso não dispensável durante a captura (não é um gate de aprovar/negar, que contradiria a própria natureza de supervisão); o evento é sempre registrado em `command_consent_events` como notificação auditável, mesmo quando a captura já estava autorizada no momento do pareamento. **Exceção conhecida: gravação de tela.** O Android não permite que nem um Device Owner conceda `MediaProjection` silenciosamente — `createScreenCaptureIntent()` sempre exibe um diálogo do sistema operacional (fora do controle do app) a cada execução, inclusive em versões recentes do Android a cada reinício do app. Para este comando especificamente, o próprio diálogo do SO já cumpre (e excede) o requisito de consentimento visível — não é uma violação do princípio "sem gate de aprovar/negar", é uma restrição de plataforma que se sobrepõe. Isso precisa estar documentado como exceção explícita, não escondido. **Caminho de recusa:** se a criança tocar em "Cancelar" nesse diálogo, o app marca o `device_command` correspondente como `denied` (valor já existente no enum `device_command_status`) via `update-command-status` — o responsável vê no painel que a gravação foi recusada, em vez de a supervisão falhar silenciosamente sem nenhum retorno.
- Mesmo contrato de dados que o simulador web já usa (`devices`, `device_commands`, `device_telemetry`, `command_consent_events`) — não é para inventar um schema paralelo.
- Distribuição: APK assinado para testes agora; AAB/Play gerenciado ou distribuição empresarial depois.
- Fabricantes como Xiaomi/Huawei/Samsung/Oppo matam foreground services e atrasam push FCM por padrão a menos que o usuário libere manualmente o app nas configurações de otimização de bateria do fabricante. Isso ameaça diretamente os critérios de sucesso de persistência/telemetria e precisa de um passo de onboarding dedicado (ver módulo `onboarding`).

## Premises
1. O schema de dados (`devices`/`device_commands`/`device_telemetry`/`command_consent_events`) já existe, é sólido, e deve ser reusado como está pelo app Android. **Confirmado.**
2. Este projeto não é só "o app Android" — o backend atual não tem NENHUMA superfície que um dispositivo real possa chamar (ver achados abaixo). Prover isso entra no escopo deste trabalho. **Confirmado.**
3. O princípio de "sem captura oculta, consentimento auditável" já é regra do próprio repositório (`AGENTS.md`), não apenas um pedido do usuário. **Confirmado.**

### Achados do repositório (auditoria do código-fonte, 2026-10-02)
- **Existe e funciona**: schema Postgres completo (`drizzle/migrations/0000_create_ninho_core.sql`, `0001_secure_device_ownership.sql`), RLS por `owner_id = auth.uid()`, Realtime habilitado nas 4 tabelas, bucket de storage `device-media`, coluna `devices.pairing_code` (gerada automaticamente, 8 chars, única).
- **Existe mas não é usado**: client Supabase com service-role (`src/integrations/supabase/client.server.ts`) e middleware de validação de JWT (`auth-middleware.ts`) — scaffolding pronto, zero imports hoje.
- **Não existe**: qualquer endpoint/Edge Function/rota que um dispositivo (sem sessão do navegador do responsável) possa chamar. O "device" hoje é só o navegador do pai simulando (`ChildSimulator` em `src/routes/index.tsx`) usando a própria sessão do pai. Não há resgate de `pairing_code`, não há credencial de device, não há revogação de vínculo.
- `roadmap.md` e `.lovable/plan/*.md` confirmam: a integração nativa foi deixada propositalmente para quando "o projeto Android for enviado" — ou seja, este design doc é exatamente esse próximo passo.

## Approaches Considered

### Approach A: Edge Function + proxy service-role + FCM para wake-up (ESCOLHIDA)
Resumo: Edge Function `redeem-pairing-code` troca o `pairing_code` por um `device_secret` aleatório (hash salvo em tabela nova `device_credentials`). Toda escrita do device (telemetria, status de comando, consentimento) passa por Edge Functions que validam esse secret e usam o client service-role já existente (`client.server.ts`) para gravar, sem alterar as RLS policies atuais do painel do pai. Um Database Webhook do Supabase dispara ao inserir em `device_commands` e envia push FCM; o app acorda, puxa comandos pendentes via Edge Function, executa, confirma.
Esforço: M | Risco: Baixo
Prós: reaproveita 100% do schema e do client service-role já existentes; zero mudança nas RLS do painel do pai; revogação server-side é 1 linha (bloqueia novas chamadas de API imediatamente), embora remover o Device Owner do aparelho em si dependa do app detectar o estado `revoked` (ver módulo `deviceadmin`); é o padrão real usado por apps de MDM/controle parental (push para acordar + API própria para payload).
Contras: cada tipo de escrita precisa de sua própria Edge Function; isolamento por `device_id`/`owner_id` fica garantido pela lógica da função, não pelo Postgres diretamente.
Reusa: `devices.pairing_code`, `client.server.ts` (supabaseAdmin), schema inalterado.

### Approach B: Device como usuário Auth sintético no Supabase (não escolhida — evolução futura)
Resumo: Ao resgatar o `pairing_code`, criar via Admin API um usuário Auth dedicado ao aparelho físico, devolvendo uma sessão Supabase real (JWT + refresh token). Novas RLS policies ligam esse `auth.uid()` do device à sua linha em `devices`. Android usa o SDK oficial Kotlin do Supabase, incluindo Realtime nativo para comandos instantâneos.
Esforço: L | Risco: Médio
Prós: mesmo modelo de RLS que já protege os dados do pai; Realtime nativo sem inventar transporte; menos código client custom.
Contras: exige migration + policies novas em 4 tabelas; revogar é desativar um usuário Auth "fantasma", não apagar uma linha; mais peças novas de uma vez num backend que hoje não tem nenhuma API device-facing.

**Nota para evolução futura (não muda a decisão atual):** existe uma opção intermediária entre A e B não explorada em profundidade — um JWT customizado assinado (claim `device_id`) validado diretamente por RLS no Postgres, sem precisar criar um usuário Auth sintético por aparelho nem validar o secret manualmente em cada Edge Function. Pode valer a pena reavaliar quando/se Approach A se mostrar difícil de manter em produção.

### Approach C: Gateway próprio fora do Supabase (descartada)
Resumo: Serviço HTTP separado concentrando toda API de device, falando com Supabase só server-to-server.
Esforço: XL | Risco: baixo tecnicamente, alto em escopo.
Contras: contradiz a arquitetura Lovable Cloud já em uso; duplica infraestrutura para hospedar/monitorar; não reaproveita nada do que já existe.

## Recommended Approach
**Approach A.** Entrega o fluxo completo (pareamento → telemetria → comando → consentimento) reaproveitando o que já existe no repo, sem mexer no que já funciona para o painel do pai, e ships mais rápido para o objetivo imediato de ter um APK assinado testável. Approach B fica como evolução natural depois que o fluxo estiver validado em campo com aparelhos reais.

## Backend — trabalho novo necessário (pré-requisito paralelo ao app Android)
1. Migration nova: tabela `device_credentials` (`device_id` FK, `secret_hash`, `fcm_token`, `created_at`, `revoked_at`).
   `redeem-pairing-code` precisa de rate limiting/lockout por IP e por `pairing_code` (ex.: N tentativas por minuto) — é o único portão que vincula um aparelho físico à conta de uma família, então mesmo com boa entropia no código (8 chars), vale a defesa básica contra força bruta.
2. Edge Functions: `redeem-pairing-code`, `ingest-telemetry`, `update-command-status`, `submit-consent-event`, `pull-pending-commands`, `update-fcm-token` (chamada pelo app sempre que `FirebaseMessagingService.onNewToken()` disparar — token FCM expira/rotaciona e nenhuma das outras funções reemite isso hoje).
3. Database Webhook em `device_commands` (INSERT) → Edge Function que dispara push FCM usando `fcm_token` salvo em `device_credentials`. **Regra de segurança não-negociável para todas as Edge Functions de escrita** (`ingest-telemetry`, `update-command-status`, `submit-consent-event`): o `device_id` usado na gravação é sempre derivado server-side via lookup em `device_credentials` pelo hash do `device_secret` recebido no header — nunca aceito como campo do corpo da requisição. Sem isso, um device pareado poderia forjar telemetria/consentimento em nome de outro device da mesma família. Se o envio falhar (token inválido, device offline), o comando permanece `pending` e é pego no próximo pull agendado pelo WorkManager (ver módulo `service`) — isso é a rede de segurança para push perdido, não apenas o caminho feliz.
4. Projeto Firebase (FCM) vinculado ao app Android.
5. Endpoint/rota de revogação (unlink) — hoje não existe nenhuma, nem para o painel web. Revogar no servidor (invalidar linha em `device_credentials`) só impede novas chamadas de API; não remove o Device Owner do aparelho. O app precisa, ao detectar `revoked` em qualquer resposta de API, chamar `clearDeviceOwnerApp()` via DPM (ou orientar o responsável a fazer reset de fábrica, se a política ativa não permitir remoção própria).
6. Rotação de `device_secret` comprometido: `devices.pairing_code` hoje é gerado automaticamente pelo banco na criação da linha (default de coluna), sem mecanismo de regeneração para uma linha já existente. O plano de rotação (revogar + reparear) só funciona de verdade se isso for resolvido — adicionar uma pequena Edge Function/mutação `regenerate-pairing-code(device_id)` que atualiza o `pairing_code` da linha existente, preservando `device_id` e todo o histórico de telemetria/comandos. Sem isso, "rotacionar" significaria recriar o device do zero e perder a continuidade de dados — inaceitável.
7. Comandos que nunca são confirmados (aparelho perdido, desinstalado, permanentemente offline): `device_commands` que ficam `pending` indefinidamente precisam expirar automaticamente (ex.: `expired` após N dias) e esse estado precisa aparecer no painel do responsável — hoje não há TTL nem esse status sendo tratado.

## Estrutura mínima do app Android (módulos)
1. **onboarding** — telas explicando e solicitando localização, notificações, câmera, microfone, demais permissões, antes do fluxo de Device Owner. Inclui detecção de fabricante (Xiaomi/Huawei/Samsung/Oppo etc.) e passo guiado para liberar o app nas configurações de otimização de bateria específicas do OEM. As permissões sensíveis (câmera, microfone, localização) são concedidas via `DevicePolicyManager.setPermissionGrantState(..., GRANT_STATE_GRANTED)` em vez de diálogos de runtime comuns — isso impede que a criança revogue a permissão depois em Ajustes > Apps, que é o buraco de escape mais óbvio e mais fácil de explorar (não exige nenhuma habilidade técnica, ao contrário de ADB/reset/safe boot).
2. **deviceadmin** — `DeviceAdminReceiver` + wrapper de `DevicePolicyManager`; aplicação de políticas (kiosk/LockTask opcional); aplica `addUserRestriction(DISALLOW_FACTORY_RESET)`, `DISALLOW_SAFE_BOOT` e `DISALLOW_DEBUGGING_FEATURES` logo após ativar Device Owner — as duas primeiras impedem reset/boot seguro, a terceira impede ativar Opções do Desenvolvedor/USB debugging e usar `adb` para interferir no app (sem ela, a criança contornaria a supervisão por ADB mesmo sem conseguir resetar o aparelho); fluxo de desligamento quando o servidor sinaliza `revoked` (chama `clearDeviceOwnerApp()` ou orienta reset de fábrica).
3. **pairing** — tela de inserir/ler código, chama `redeem-pairing-code`, guarda `device_secret` cifrado.
4. **service** — inclui uma `FirebaseMessagingService` (recebe o push e `onNewToken()`, chama `update-fcm-token`) que acorda o `Foreground Service` com notificação persistente; um `BootReceiver` (`ACTION_BOOT_COMPLETED`/`LOCKED_BOOT_COMPLETED`) reinicia o Foreground Service e dispara um pull imediato após reboot — sem isso, "sobrevive a reboot" não acontece sozinho. O Foreground Service agenda pulls de segurança via WorkManager (intervalo cobre o caso de push perdido) e mantém uma única fila local (Room/SQLite) de envio para telemetria, status de comando **e** eventos de consentimento pendentes — o módulo `audit` (abaixo) usa essa mesma fila para reenvio, não uma fila paralela. Cada item da fila carrega uma chave de idempotência gerada no cliente (UUID); `ingest-telemetry`/`update-command-status`/`submit-consent-event` deduplicam por essa chave no servidor, para que um reenvio após falha de ack (sucesso no servidor, confirmação perdida no cliente) não grave registro duplicado — crítico especialmente para `command_consent_events`, cuja trilha teria que ser confiável para servir de auditoria.
5. **location** — `FusedLocationProviderClient`, fluxo de permissão de localização em primeiro/segundo plano.
6. **api** — client HTTP (Retrofit/OkHttp) para as Edge Functions, injeção do `device_secret` no header, com retry/backoff para falhas de `ingest-telemetry`/`update-command-status`.
7. **storage** — Android Keystore + EncryptedSharedPreferences para a credencial do device.
8. **audit** — log local das ações executadas e do consentimento mostrado, espelhando `command_consent_events`; falhas de envio de `submit-consent-event` entram na mesma fila de reenvio do módulo `service`, não num caminho de retry separado.

## Open Questions
1. Payload de provisionamento QR — rascunho inicial (ver Apêndice A para o JSON completo). Decisão pendente: incluir `PROVISIONING_WIFI_SSID`/`PROVISIONING_WIFI_PASSWORD` no QR (aparelho recém-resetado não tem Wi-Fi configurado) é sensível — senha de rede dentro de um QR escaneável — então a alternativa é exigir que o responsável conecte o aparelho ao Wi-Fi manualmente antes de escanear. Decidir qual caminho seguir no MVP.
2. Minimum SDK / versões Android alvo da frota real de aparelhos supervisionados.
3. Escopo exato do modo kiosk (LockTask simples vs. launcher substituto completo) — ainda não detalhado.
4. Quem é o dono da conta Firebase/FCM (novo projeto ou integrar a um existente da Assurant)?
5. Endpoint de revogação/unlink não existe nem no painel web hoje — **decidido: entra neste escopo** (ver Backend item 5, módulo `deviceadmin` e Success Criteria, que já especificam o comportamento completo). Falta apenas construir a tela/ação correspondente no painel web, que hoje não tem nenhum controle de remover/desvincular device.
6. Como o APK assinado de teste é atualizado em um aparelho que já é Device Owner? Sideload manual exige reinstalar (possivelmente com perda de Device Owner) enquanto a fase "depois" (Play gerenciado/EMM) resolveria isso nativamente — decidir o caminho da fase de testes antes de distribuir a primeira versão.

## Success Criteria
- QR code no setup de fábrica ativa Device Owner automaticamente, sem passo manual, em aparelho sem contas configuradas.
- Código de pareamento vincula o aparelho à conta do responsável no painel real (não mais simulado).
- Foreground service sobrevive a reboot, reporta localização/bateria em intervalo agendado (WorkManager) e reage a push FCM em poucos segundos quando há conectividade.
- Comandos (`device_commands`) chegam ao aparelho via push (ou pull de segurança, se o push falhar) e são executados com indicador visível + consentimento registrado em `command_consent_events`.
- Telemetria capturada offline é enfileirada localmente e sincronizada assim que a conectividade voltar, sem perda de dados.
- Revogação do vínculo (servidor sinaliza `revoked`) resulta em `clearDeviceOwnerApp()` ou instrução clara de reset de fábrica — não apenas em parar de aceitar chamadas de API.
- Enquanto o vínculo estiver ativo, a criança não consegue remover o app nem escapar da supervisão pelos caminhos do próprio Android (Ajustes → reset de fábrica, boot em modo seguro, ADB/Opções do Desenvolvedor — `DISALLOW_FACTORY_RESET`/`DISALLOW_SAFE_BOOT`/`DISALLOW_DEBUGGING_FEATURES` aplicados) nem revogando permissões manualmente (`setPermissionGrantState`). **Limitação conhecida e fora do controle do Device Owner:** reset via modo recovery físico (combinação de botões volume+power), que vários fabricantes permitem independente de qualquer política de MDM — não há mitigação de software para isso.
- APK assinado instalável em aparelho de teste via QR, fim a fim.

## Distribution Plan
- Agora: APK assinado para testes, hospedado para o QR de provisionamento ler (URL HTTPS + checksum). Atualização nesta fase depende da decisão da Open Question 6 (sideload manual vs. instalação silenciosa via DPM); não é automática por padrão.
- Depois: AAB para Google Play gerenciado (Android Enterprise/EMM) ou distribuição empresarial direta — resolve atualização automática nativamente.

## Dependencies
- Backend novo (seção acima) é bloqueador — sem ele o app não tem com quem falar.
- Projeto Firebase para FCM — **bloqueador organizacional para a Lane C** (ver Worktree Parallelization), não é só uma pergunta aberta: sem dono definido da conta, o trabalho de `service`/push para para antes de começar.
- Decisão sobre hospedagem do APK para o QR (item 1 das Open Questions).
- **Revisão legal/compliance — bloqueador para produção, não para o MVP de teste.** O app grava câmera/microfone/tela/localização de um menor e inevitavelmente captura terceiros (amigos em chamada, outras crianças) sem consentimento deles. Antes de ir para qualquer uso real (mesmo distribuição empresarial limitada), precisa de: política de retenção/exclusão de mídia em `device-media`, checagem de leis de gravação com consentimento de duas partes na jurisdição de uso, e checagem da política da Play Store/Android Enterprise para apps de monitoramento parental. Construir e testar o APK pode prosseguir sem isso; lançar para uso real não deve.

## NOT in scope (considerado e adiado deliberadamente)
- **Approach B (device como usuário Auth sintético / Realtime nativo)** — adiado como evolução futura; Approach A entrega o mesmo resultado funcional mais rápido e com menos peças novas no backend.
- **Modo kiosk completo (launcher substituto)** — escopo exato ainda em aberto (Open Question 3); o módulo `deviceadmin` só compromete LockTask básico neste design.
- **Tela de revogação/unlink no painel web** — o comportamento do lado do servidor e do app está especificado, mas construir a UI correspondente no painel web é trabalho novo não detalhado aqui.
- **AAB/Play gerenciado** — fase "depois" da Distribution Plan; fora do escopo do primeiro APK de teste.

## Worktree Parallelization Strategy

| Step | Módulos tocados | Depende de |
|------|------------------|------------|
| Backend: migration + Edge Functions | `drizzle/migrations/`, novo diretório de Edge Functions no repo Ninho | — |

## Apêndice A — Rascunho do payload de provisionamento QR

Este é o JSON que o QR code precisa codificar para o Android ativar Device Owner automaticamente no setup de fábrica. Valores entre `<>` são preenchidos por device/sessão de pareamento.

```json
{
  "android.app.extra.PROVISIONING_DEVICE_ADMIN_COMPONENT_NAME": "com.ninho.companion/.deviceadmin.NinhoDeviceAdminReceiver",
  "android.app.extra.PROVISIONING_DEVICE_ADMIN_SIGNATURE_CHECKSUM": "<sha256-base64-da-assinatura-do-apk>",
  "android.app.extra.PROVISIONING_DEVICE_ADMIN_PACKAGE_DOWNLOAD_LOCATION": "https://<host-do-apk>/ninho-companion-release.apk",
  "android.app.extra.PROVISIONING_DEVICE_ADMIN_PACKAGE_CHECKSUM": "<sha256-base64-do-apk>",
  "android.app.extra.PROVISIONING_SKIP_ENCRYPTION": false,
  "android.app.extra.PROVISIONING_LEAVE_ALL_SYSTEM_APPS_ENABLED": true,
  "android.app.extra.PROVISIONING_ADMIN_EXTRAS_BUNDLE": {
    "pairing_session_hint": "<opcional: referência à sessão de pareamento iniciada no painel, não o pairing_code em si>"
  }
}
```

Decisão pendente (Open Question 1): se o aparelho de teste não estiver em uma rede com Wi-Fi já salvo, adicionar `android.app.extra.PROVISIONING_WIFI_SSID` / `PROVISIONING_WIFI_PASSWORD` a este mesmo JSON — ou exigir que o responsável conecte o Wi-Fi manualmente antes de escanear, evitando colocar a senha da rede dentro do QR.
